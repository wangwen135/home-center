# 项目上下文

## 项目定位

Home Center 是个人使用的家庭中心系统。系统会部署到个人服务器上，并通过公网访问。

它不是单纯的后台管理系统，也不是普通的网站导航页，而是个人公网入口、私有资源入口、统一登录认证、单点登录中心和设备控制入口的组合。

系统不只给本人使用，后续也会给家人或朋友创建账号。因此权限、导航隔离、审计和后台管理不能按纯单用户系统简化。

后续设计和开发时，必须优先考虑以下目标：

- 公网入口要清晰、可信、轻量。
- 私有入口要安全、稳定、便于快速进入常用管理工具。
- 后台管理要偏效率，不追求花哨展示。
- 登录和认证能力要能支撑 nginx 反向代理下的私有服务访问。
- 登录和认证能力也要能支撑后续自研应用接入 Home Center 做单点登录。
- PC Agent 能力要和服务端接口保持一致，避免只改一端。
- 多用户能力要可靠，普通用户、家人/朋友账号和超管账号的可见功能与可操作数据必须清晰区分。

基础角色先定义为三类：

- 未登录用户：只能访问公开首页和公开资源。
- 普通用户：登录后维护自己的私有导航，访问被授权的私有入口和功能。
- 超管：拥有系统管理能力，可以管理用户、权限、会话、设备、审计、配置等。

暂不引入普通管理员角色，后续确有需要再扩展。

## 部署信息安全

仓库文档只记录架构规则、接口契约和占位符，不记录真实部署信息。

不要提交到 GitHub 的内容包括：

- 真实公网域名。
- 真实内网 IP。
- 真实服务器路径。
- 真实 nginx 配置路径。
- token、密钥、cookie 示例值。
- 私有主机名。
- 任何能直接暴露个人服务器、家庭网络或内部系统的信息。

文档示例统一使用占位符，例如：

- `<public-domain>`
- `<internal-service-domain>`
- `<internal-service-upstream>`
- `<server-path>`
- `<token>`

真实部署信息应保存在服务器配置、私有部署文档或本地安全位置，不进入仓库。

## 访问层级

### 公开首页导航

公开首页是系统对公网开放的默认入口。

主要内容：

- 自己开发的公开工具链接。
- 收藏的公开链接地址。
- 可以公开展示的服务入口。
- 独立应用入口，例如后续的图床应用。

设计要求：

- 不要求访客先登录。
- 页面要像个人门户，重点是清晰、快速、可访问。
- 点击独立应用入口后，可以进入该应用自己的登录界面。
- 首页需要兼容手机端。

### 登录入口

系统需要一个明确的登录界面。

登录成功后，用户进入私有导航页面。

设计要求：

- 登录页需要兼容手机端。
- 登录流程必须清晰。
- 登录失败必须有明确提示。
- 登录成功后的跳转目标必须稳定。
- 不保留没有后端支撑的伪功能。

### 私有导航页面

私有导航页面是登录后的个人内网工具入口。

主要内容：

- 内网管理工具入口。
- 服务器管理入口。
- 需要认证后才能访问的私有服务。
- 通过 nginx 反向代理暴露出来的内部系统。
- 普通外链、内网直连地址、SSH/RDP 等说明类入口。

设计要求：

- 强调效率和分组。
- 用户需要快速找到目标系统。
- 私有资源的访问应依赖 Home Center 的登录状态或 token。
- 不把私有系统误放到公开导航中。
- 私有导航不要求所有入口都通过 nginx 代理。它可以同时包含 nginx 代理入口、普通外链、内网直连地址和说明类入口。

### 导航数据模型

公开导航和私有导航直接使用两套独立数据表存储，不共用一张表再通过 `visibility`、`type` 或类似字段区分。

设计影响：

- 公开导航和私有导航可以有不同字段、排序、分组和权限策略。
- 后台管理中应明确区分公开导航管理和私有导航管理。
- 接口路径和服务层职责应清晰拆分，避免在同一套 CRUD 中混合公开和私有入口。
- 公开导航默认不要求登录，私有导航默认要求登录。
- 迁移脚本、初始化数据和测试数据也应按两套表分别维护。

公开导航和私有导航的基础字段大体保持一致，便于复用管理体验和前端展示逻辑。

基础字段建议：

- 名称。
- URL 或目标地址。
- 图标，采用用户直接上传的图片。
- 分组。
- 排序。
- 描述。
- 打开方式。
- 是否启用。

私有导航额外支持私有场景字段，例如入口类型。入口类型可以包括 nginx 代理、普通外链、内网直连、SSH/RDP 说明等。

导航入口打开规则：

- 可跳转入口默认都在新窗口打开。
- 说明/命令类入口不直接跳转，点击后弹出说明或提供复制命令能力。
- 说明/命令类入口需要在界面上和普通链接做出区分，避免用户误以为会打开网页。

导航图标规则：

- 图标由用户直接上传图片。
- 不默认自动抓取网站 favicon。
- 不依赖外部图标 CDN 或第三方图标服务。
- 后台需要提供上传、预览、替换和删除图标能力。
- 前端展示时需要有默认占位图标，避免未上传图标导致布局不齐。
- 上传图片存储在服务器本地文件目录中，数据库只保存访问路径和必要元数据。
- 不把导航图标图片二进制直接存入数据库。
- 上传格式允许 PNG、JPG/JPEG、WEBP、SVG 等常见图片格式。
- 单个导航图标文件最大 10MB。
- SVG 上传需要做安全处理，禁止脚本、事件属性和外链资源等不安全内容。

私有导航由当前登录用户自行维护，不同用户看到的私有导航界面可以完全不同。

私有导航设计影响：

- 私有导航数据必须归属到用户，查询、创建、修改、删除都要按当前登录用户隔离。
- 普通用户只能维护自己的私有导航入口。
- 管理员是否能查看或维护其他用户的私有导航，需要单独设计后台能力，不能默认混在普通用户接口中。
- 私有导航入口本身不等同于系统功能权限；它主要是用户自己的入口集合。
- 顶部功能菜单、设备管理、后台管理等系统级功能必须走角色或权限控制。没有对应权限时，不显示对应菜单，也不能通过直接访问绕过后端校验。
- 私有导航入口应能标记入口类型，例如 nginx 代理、普通外链、内网直连、说明/命令类入口，便于前端展示不同图标、打开方式和提示。
- 导航入口需要支持后台定时健康检查。健康状态由服务端定时任务检查并缓存，前端只展示已有状态，不在页面加载时逐个发起探测。
- 健康检查优先服务于后台和私有导航状态展示。
- 公开首页保持干净，不展示链接健康状态。
- 私有导航只展示轻量健康状态，例如小圆点或状态 badge，不展示详细错误。
- 健康检查详情、失败原因、HTTP 状态码和耗时只在后台管理中查看。

### 后台管理

后台管理用于维护 Home Center 自身的数据和能力。

可能包含：

- 用户管理。
- 角色和权限管理。
- 公开导航管理。
- 私有导航管理。
- 系统配置管理。
- 设备管理。
- PC Agent 相关状态和控制能力。
- 日志、提示消息、内部系统等管理模块。

设计要求：

- 后台只需要按桌面端设计。
- 后台页面偏管理工具，不要求手机端适配。
- 操作要清晰、稳定、可追踪。
- 危险操作必须二次确认。

## 认证与 nginx 代理

Home Center 需要承担统一登录、认证中心和自研应用单点登录中心的职责。

预期方式：

- 用户先在 Home Center 登录。
- Home Center 生成或维护认证 token。
- nginx 代理内部服务时，使用 Home Center 的 token 做认证。
- 私有服务入口可以由 Home Center 私有导航统一组织。
- 后续自研应用应优先接入 Home Center 的登录校验能力，而不是各自实现独立登录。
- nginx 鉴权主要用于保护那些已有的、无法改造登录逻辑的内部系统。

设计和开发注意事项：

- 不要把 token、密钥、私有主机名写入前端代码或文档示例。
- 私有导航的访问权限应和用户登录态、角色或权限挂钩。
- 公开导航和私有导航的数据边界要清晰。
- 后续涉及 nginx 认证逻辑时，需要单独设计接口契约和安全策略。
- 后续涉及自研应用 SSO 接入时，需要单独设计应用接入、token 校验、用户信息获取、权限同步和退出登录联动策略。

### 自研应用单点登录

Home Center 后续要作为自研应用的单点登录中心，为其他自研应用提供登录校验能力。

定位：

- 自研应用优先通过 Home Center 完成登录态校验。
- Home Center 提供统一用户身份、角色和权限来源。
- 自研应用不重复维护独立账号体系，除非该应用有明确的独立登录需求。
- nginx `auth_request` 主要用于已有系统、第三方系统或无法改造认证逻辑的内部系统。

设计影响：

- 需要提供面向自研应用的登录校验接口。
- 需要提供当前用户信息接口，例如用户 ID、用户名、昵称、角色、权限等。
- 需要定义应用接入标识，避免任意系统滥用校验接口。
- 需要考虑应用级权限范围，不同自研应用可能读取不同用户信息。
- 需要考虑统一退出登录后，自研应用如何感知登录失效。
- 需要明确跨域、cookie、跳转回调和原始目标地址策略。
- 需要保证自研应用接入方式和 nginx 鉴权方式可以并存。

第一版 SSO 接入采用轻量方案：

- 自研应用通过浏览器共享 `home_center_token` cookie。
- 自研应用调用 Home Center 的登录校验接口或当前用户接口确认登录态。
- 推荐提供 `/api/sso/me` 这类接口返回当前用户基础信息和权限。
- 自研应用接入需要配置 `appId` 和 `appSecret`。
- `appId` 用于识别接入应用和控制应用级权限范围。
- `appSecret` 用于服务端到服务端的可信调用，不应暴露到浏览器前端。
- 不引入 OAuth2、OIDC 等复杂协议，除非后续确有必要。
- 该方案适合个人部署的自研应用生态，重点是简单、稳定、易接入。
- 自研应用大概率部署在同一主域名的不同子域下，例如 `<app>.<public-domain>`。
- SSO cookie 需要支持跨子域共享，后续应按 `Domain=.<public-domain>`、`SameSite=Lax`、`Secure` 等策略设计。
- 文档和示例仍使用占位符，不记录真实主域名。
- 生产环境默认全站 HTTPS。
- 生产环境写入 `home_center_token` cookie 时必须设置 `Secure`，本地开发环境可以不设置。
- 默认使用 `SameSite=Lax`。只有未来确实需要跨站 iframe 或第三方上下文时，才考虑 `SameSite=None; Secure`。

`/api/sso/me` 默认返回最小必要用户信息：

- `userId`
- `username`
- `nickname`
- `avatar`
- `roles`
- `permissions`

手机号、邮箱等敏感信息默认不返回。只有应用被明确授权后，才允许返回额外敏感字段。

自研应用调用 SSO 登录校验和 `/api/sso/me` 需要记录审计日志。

SSO 审计至少记录：

- `appId`
- 用户 ID 或用户名。
- 调用接口。
- 调用时间。
- 来源 IP。
- User-Agent。
- 是否成功。
- 失败原因。
- 返回信息范围。

统一退出登录采用轻量策略：

- Home Center 退出登录、会话过期、超管踢出、权限变更等场景使 `home_center_token` 失效。
- 自研应用不需要接收主动通知。
- 自研应用在下一次调用 `/api/sso/me`、登录校验接口或自身后端鉴权时感知 token 失效。
- 感知失效后，自研应用展示登录失效提示并引导用户重新登录。

### Token 与会话策略

Home Center 最终按单体应用设计，认证 token 使用短期自定义 token，不使用 JWT，也不依赖 Redis。

token 存储策略：

- token 直接存储在服务端内存中。
- token 只作为登录会话标识，不把复杂业务数据放进 token 本身。
- 服务重启后，内存 token 全部失效，用户需要重新登录。
- 由于系统是个人部署的单体应用，暂不考虑多实例 token 同步。

过期策略：

- token 使用短期有效期。
- 后端在用户有效访问时自动刷新 token 的滑动过期时间。
- 必须设置最长会话生命周期，当前约定最长为 12 小时。
- 即使页面自动刷新或前端轮询持续访问，token 也不能超过 12 小时硬上限。
- 超过最长生命周期后必须重新登录。

管理要求：

- 后台需要增加“当前登录情况”或“在线会话管理”界面。
- 超管可以查看当前在线会话，并可以踢出指定登录会话。
- 登录会话应记录登录时间、最近访问时间、登录 IP、User-Agent、用户、token 过期时间和最长有效截止时间。
- 退出登录、超管踢出、token 过期都应让 nginx `/checkAuth` 返回未认证状态。
- 同一用户只允许保留一个有效登录会话。新登录成功后，应踢出该用户旧的登录会话。
- 用户被禁用、角色变更、权限变更或密码变更后，应立即踢出该用户当前登录会话，不等待 token 自然过期。
- 前端需要提供公共的“登录已失效/已被踢出”提示能力，优先使用统一弹框或全局提示，不在每个页面重复实现。

## nginx 认证接入方案

Home Center 与 nginx 的关系是：Home Center 负责登录、token 签发和 token 校验，nginx 负责把公网域名代理到具体内部系统，并在代理前调用 Home Center 做访问认证。

### 通用认证配置

nginx 通用配置应包含一个内部鉴权 location：

```nginx
location /checkauth {
    internal;

    proxy_pass http://127.0.0.1:8866/checkAuth;

    proxy_set_header Host $http_host;
    proxy_set_header X-Original-URI $request_uri;

    proxy_pass_request_body off;
    proxy_set_header Content-Length "";
}
```

关键约定：

- `/checkauth` 只给 nginx 内部认证流程使用，必须设置 `internal`。
- `/checkauth` 代理到 Home Center 服务端的 `/checkAuth`。
- nginx 通过 `X-Original-URI` 告诉 Home Center 用户原本访问的地址。
- 鉴权请求不转发请求体，只用于判断当前 cookie 或 token 是否有效。
- Home Center 的 `/checkAuth` 应返回适合 nginx `auth_request` 使用的状态码。

### token 写入与跳转

nginx 需要提供一个写入 token 并重定向的入口：

```nginx
location /home-center/token {
    add_header Set-Cookie "home_center_token=$arg_token; Path=/; HttpOnly";

    set $toUrl "/";
    if ($arg_ref) {
        set $toUrl $arg_ref;
    }
    return 302 $toUrl;
}
```

关键约定：

- cookie 名称为 `home_center_token`。
- token 从查询参数 `token` 读取。
- `ref` 参数表示写入 cookie 后要返回的目标地址。
- 如果没有 `ref`，默认跳转到 `/`。
- cookie 必须设置 `HttpOnly`。
- 生产环境默认全站 HTTPS，cookie 必须设置 `Secure`。
- 本地开发环境可以不设置 `Secure`，便于通过 HTTP 调试。
- 自研应用按同一主域名不同子域部署时，cookie 使用 `Domain=.<public-domain>` 和 `SameSite=Lax`，以支持跨子域共享登录态。

### 内部子系统反向代理

每个内部子系统可以用独立域名或独立 server block 暴露到公网，由 nginx 代理到内网地址。

示例结构：

```nginx
server {
    include conf.d/home-center.common;

    server_name <internal-service-domain>;

    location / {
        proxy_pass http://<internal-service-upstream>/;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_cache_bypass $http_upgrade;

        include conf.d/home-center.auth;
    }
}
```

关键约定：

- `conf.d/home-center.common` 放通用能力，例如 `/checkauth`、`/home-center/token` 等。
- `conf.d/home-center.auth` 放实际认证逻辑，例如 `auth_request /checkauth`、未登录跳转、错误处理等。
- 子系统自身可以不知道 Home Center 的登录细节，访问控制由 nginx 和 Home Center 共同完成。
- 私有导航页中的内部系统链接应指向这些 nginx 代理域名。
- 用户已登录且 cookie 有效时，应直接进入目标系统。
- 用户未登录或 token 失效时，应跳转到 Home Center 登录；登录成功后写入 token，再回到原始目标地址。

### 特殊子系统兼容

部分内部系统的前端代码可能假设自己运行在原始 host、原始端口或特定路径下。nginx 代理时可能需要额外兼容。

例如某些路由器或网关页面可能需要：

- 对首页或指定 JavaScript 文件使用 `sub_filter`。
- 替换原始脚本中的 host、port 或路径判断。
- 关闭上游 gzip，确保 `sub_filter` 能处理文本内容。
- 对指定静态资源单独设置 location。

示例结构：

```nginx
location /some-static-file.js {
    proxy_pass http://<internal-service-upstream>/some-static-file.js;

    proxy_set_header Accept-Encoding "";
    sub_filter "<origin-snippet>" "<replacement-snippet>";
    sub_filter_once off;
    sub_filter_types *;
}
```

设计注意事项：

- 这类兼容规则属于具体子系统适配，不应写入通用认证配置。
- 能不用 `sub_filter` 时尽量不用，因为它依赖上游页面实现细节。
- 如果使用 `sub_filter`，必须记录原因和影响范围。
- 对内部系统做代理适配时，不要破坏 Home Center 的认证链路。

### 认证链路

典型访问流程：

1. 用户访问某个内部系统代理域名。
2. nginx 在代理前调用 `/checkauth`。
3. `/checkauth` 转发到 Home Center `/checkAuth`。
4. Home Center 校验 `home_center_token` 或相关认证信息。
5. token 有效时，nginx 放行请求到内部系统。
6. token 无效时，nginx 跳转到 Home Center 登录页，并携带原始访问地址。
7. 用户登录成功后，Home Center 或 nginx 进入 `/home-center/token?token=...&ref=...`。
8. nginx 写入 `home_center_token` cookie。
9. nginx 重定向回 `ref` 指向的原始内部系统。

### 开发影响

Home Center 后续功能设计必须支持这套代理认证模型：

- `/checkAuth` 是 nginx 认证链路的关键接口，不能随意改路径和语义。
- 登录成功后需要支持带原始目标地址的跳转。
- token 的生命周期、刷新、失效和退出登录策略需要明确。
- 私有导航中的内部系统入口应支持登录态校验和过期重登。
- 后台管理可以维护内部系统入口、公开入口、是否需要认证、排序和分组。
- 前端不能把 token 暴露给普通脚本逻辑，能使用 HttpOnly cookie 时优先使用 cookie。

## Home Center PC Agent

Home Center PC Agent 是配套项目，部署在需要被控制的电脑上。

它的职责是执行目标电脑上的本地操作，并与 Home Center 服务端通信。

PC Agent 与 Home Center 服务端的通信方式确定为 WebSocket 长连接。Agent 主动连接服务端，服务端通过这条长连接下发控制指令，Agent 通过同一连接返回执行结果或状态。

主要能力：

- 电脑截图。
- 下发并执行指令。
- 获取设备状态。
- 执行电源相关操作。
- 上报版本、连接状态和执行结果。
- 承接后续更多 PC 控制能力。

服务端职责：

- 管理设备记录。
- 展示设备在线状态。
- 向 Agent 下发控制指令。
- 接收 Agent 返回的截图、状态和执行结果。
- 在后台或设备页面提供可操作的控制界面。

开发注意事项：

- 修改 PC 控制接口时，必须同时考虑 Home Center 服务端和 PC Agent 项目。
- endpoint 路径、请求体、响应体、认证方式、端口和错误码要保持一致。
- 前端设备控制页面不能假设 Agent 一定在线。
- 设备操作必须处理离线、超时、失败、执行中和成功状态。
- 截图和命令执行属于敏感能力，前端必须放在登录后的私有区域或后台区域。
- WebSocket 长连接设计以 `docs/design/agent-websocket-plan.md` 为准。
- 服务端不应再依赖主动连接 Agent 的 IP 和端口来下发控制命令。
- Agent 首次连接时，如果服务端没有匹配到已有 `agentId`，自动创建设备记录，不进入待审核流程。
- 自动创建的设备默认启用。
- 自动创建的设备后续可在后台重命名、禁用或管理。
- PC Agent 相关敏感操作必须增加审计日志，包括截图、关机、重启、远程命令执行和后续新增的高风险控制能力。
- 审计日志至少记录操作者、目标设备、操作类型、请求时间、完成时间、执行结果、失败原因、requestId、来源 IP 和 User-Agent。
- 远程命令执行审计只记录命令摘要和执行结果，不记录完整命令输出。
- 设备控制操作需要按风险分级。普通状态查看和导航跳转不需要确认；关机、重启等电源操作必须二次确认。
- 远程命令执行计划做成 Web Shell 形态。进入 Web Shell 前必须做权限校验和风险确认；进入后执行单条命令时不要求每次重复二次确认，但必须记录审计日志。

## 页面设计影响

基于以上项目定位，前端页面应按以下方向设计：

- 公开首页：个人门户风格，轻量、清晰、移动端可用。
- 登录页：可信、安全、直接。
- 私有导航：分组明确、入口高效、突出常用管理工具。
- 后台管理：桌面端优先，表格和表单效率优先。
- 设备控制页：状态优先，操作谨慎，危险动作需要确认。

这些规则应和 `docs/UI_DESIGN.md`、`docs/frontend-development-rules.md` 一起使用。
