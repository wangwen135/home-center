# UI 设计规范

## 目标

本文件定义 Home Center 前端页面的统一 UI 设计规则，后续页面重构、AI 生成页面、人工维护页面都必须以本文为准。

本项目不是做通用组件库，也不是改造成 SPA。设计目标是：页面清晰、操作稳定、信息层级明确、视觉一致、代码可维护。前端实现优先使用原生 HTML/CSS/JavaScript；当多个页面需要稳定复用头部、底部、公共骨架或服务端渲染变量时，可以使用 Thymeleaf。

## 适用范围

- 登录页、导航页、个人信息页、错误页、设备页、管理后台页都适用本文规则。
- `/index.html` 和 `/admin.html` 保留现有导航入口展示方式，只统一头部、底部、主题切换、间距、移动端适配和明显布局问题。
- 管理后台只按桌面端设计，不要求兼容手机端。
- 登录页和导航页必须兼容手机端。
- Kindle 等固定屏幕信息密度页面不强制套用通用视觉重构，只处理编码、溢出、安全和明显交互问题。

## 产品设计原则

1. 页面先回答用户“我在哪里、能做什么、下一步是什么”。
2. 重要操作必须显眼，危险操作必须克制，并且需要二次确认。
3. 表格和表单页面优先追求效率，不做过度装饰。
4. 信息层级靠字号、字重、间距和位置表达，不靠大量颜色。
5. 页面状态必须完整：加载中、空数据、错误、成功、提交中、禁用态都要有明确表现。
6. 不保留“看起来能点但实际没有后端支持”的伪功能。
7. 动态数据必须安全渲染，接口内容写入 HTML 前必须转义。

## 技术选型边界

默认技术栈：

- HTML
- CSS
- JavaScript
- Spring Boot 静态资源
- 必要时使用 Thymeleaf

禁止默认引入：

- Vue、React、Angular 等前端框架
- Vite、Webpack、Babel、TypeScript 等前端构建链
- 新的 npm 工程
- 外部 CDN
- 与当前项目无关的 UI 框架

Thymeleaf 只在以下情况使用：

- 多个页面共享固定头部、底部、基础页面骨架。
- 页面需要服务端直接注入少量用户、权限、菜单、版本号等上下文。
- 纯静态 HTML 已经导致大量重复结构，维护成本明显升高。

Thymeleaf 不用于把项目改造成复杂模板系统；页面交互仍然由原生 JavaScript 和项目公共工具函数完成。

## 编码与文案

乱码问题会直接破坏页面可信度，所有前端页面和文档必须统一编码。

- HTML、CSS、JavaScript、Markdown 文件统一使用 UTF-8。
- HTML 必须声明 `<meta charset="UTF-8">`。
- 不使用 GBK、ANSI 或编辑器自动猜测编码保存文件。
- 修改中文文案后必须在浏览器里确认没有乱码。
- 如果 PowerShell 终端显示中文异常，不能直接判断文件损坏，应以浏览器、Node 读取或编辑器 UTF-8 显示结果为准。
- 产品文案应简短、具体、可行动，避免只有“失败”“错误”这类无帮助提示。
- 按钮文案使用动词，例如“保存”“新增”“刷新”“删除”“返回”，不使用含糊描述。

## 页面整体结构

所有普通页面应采用统一结构：

```html
<body class="hc-app">
<header class="hc-app-header"></header>
<main class="hc-app-main"></main>
<footer class="hc-app-footer"></footer>
</body>
```

如果页面使用 Thymeleaf，头部和底部应抽成公共 fragment：

```html
<header th:replace="~{fragments/layout :: appHeader}"></header>
<footer th:replace="~{fragments/layout :: appFooter}"></footer>
```

结构规则：

- `header` 使用全站统一样式，默认位于页面顶部；是否吸顶或固定由页面类型决定。
- `footer` 使用全站统一样式，默认位于页面底部；是否贴底或固定由页面类型决定。
- 当 `header` 或 `footer` 使用 `position: sticky`、`position: fixed` 时，`main` 必须预留空间，避免内容被覆盖。
- 页面主体使用单一主容器，不要多层嵌套卡片。
- 弹窗、下拉菜单、toast 的层级必须高于头部和底部。

## 固定头部

头部是全站统一的系统级导航区域，不允许每个页面随意设计一套。

这里的“固定”指样式固定，不强制所有页面使用 `position: fixed`。

桌面端头部规则：

- 高度：`56px` 或 `64px`，同一批页面必须一致。
- 左侧：系统名称、页面标题或返回入口。
- 中间：只在有必要时放导航、面包屑或上下文信息。
- 右侧：主题切换、用户入口、退出登录、页面级主要操作。
- 背景：使用接近白色或暖白色。
- 边框：底部 `1px` 轻边框。
- 阴影：最多使用非常轻的阴影，不做厚重悬浮效果。

移动端头部规则，仅登录页和导航页必须支持：

- 高度：`56px`。
- 标题单行显示，过长省略。
- 右侧操作按钮保持可点击区域不小于 `40px`。
- 导航内容允许换行或折叠，但不能横向撑破视口。

主题切换按钮：

- 全站使用同一种形态。
- 推荐图标按钮或图标加短文字，避免“明/暗”这种孤立且不自然的文案。
- 按钮尺寸统一为 `40px` 高，图标按钮宽高为 `40px`。
- 必须有 `aria-label` 和 `title`。
- 视觉上应像工具按钮，不应像主要业务按钮。

## 固定底部

底部用于承载系统状态和低频信息，不承担主要导航。

这里的“固定”指样式固定，不强制所有页面使用 `position: fixed`。

底部规则：

- 高度：`36px` 或 `40px`。
- 内容：版权、版本号、运行环境、系统状态，可按页面需要选择。
- 字号：`12px` 或 `13px`。
- 颜色：弱化文本色。
- 背景：与头部一致或略浅。
- 边框：顶部 `1px` 轻边框。
- 不放主要操作按钮。

如果某个页面主体很短，底部仍应贴近视口底部；如果主体很长，底部不能遮挡最后一屏内容。

## 页面类型

### 登录页

- 必须兼容手机端。
- 表单居中，主操作明确。
- 登录按钮提交中必须禁用并显示状态。
- 登录失败显示明确错误，不只写控制台。
- 成功后跳转逻辑必须清晰，不保留无效链接。

### 导航页

- 必须兼容手机端。
- 保留现有导航卡片或导航入口展示方式。
- 统一头部、底部、主题切换和用户区域样式。
- 卡片间距、对齐、折行、头像区、下拉菜单层级必须稳定。

### 管理后台

- 只按桌面端设计。
- 推荐最小宽度为 `1180px`，内容区域允许表格横向滚动。
- 侧边栏、顶部工具栏、内容表格、弹窗必须统一样式。
- 不为了手机端压缩后台表格，不做复杂移动端卡片化。
- 后台强调效率和密度，留白克制，操作集中。

### 设备页

- PC 电源、监控等页面以桌面和平板可用为主。
- 状态、截图、终端、操作按钮必须有清晰层级。
- 危险设备操作必须二次确认。
- 截图、终端弹窗、菜单不能溢出视口。

### 错误页

- 信息简洁，明确错误类型和下一步动作。
- 提供返回首页、返回上一页或重新登录等真实可用操作。
- 不使用大段技术堆栈信息面向普通用户。

## 信息层级

每个页面最多保留三级主要层级：

1. 页面标题：说明当前页面职责。
2. 区块标题：说明当前区域内容。
3. 字段、表格、状态和操作：承载具体任务。

字号建议：

| 类型 | 字号 | 字重 | 行高 |
| --- | --- | --- | --- |
| 页面标题 | 24px-28px | 600-700 | 1.25 |
| 区块标题 | 18px-20px | 600 | 1.35 |
| 卡片标题 | 15px-16px | 600 | 1.4 |
| 正文 | 14px | 400 | 1.5 |
| 表格文字 | 13px-14px | 400 | 1.45 |
| 辅助文字 | 12px-13px | 400 | 1.4 |
| Badge | 12px | 600 | 1.3 |

规则：

- 不使用负字间距。
- 不在管理后台使用超大营销标题。
- 同一页面内相同层级必须使用相同字号和字重。
- 辅助说明不能比主要内容更抢眼。

## 颜色规则

整体采用 Notion 风格的暖白、近黑、低饱和中性色。

推荐角色：

- 页面背景：暖白或浅灰白。
- 主文本：近黑，不用纯黑大面积铺满。
- 辅助文本：暖灰。
- 边框：低对比 `1px` 细线。
- 主按钮：统一使用项目主色。
- 危险操作：红色，只用于删除、关机、重置等危险行为。
- 成功：绿色。
- 警告：橙色或琥珀色。

规则：

- 优先复用 `/css/app-theme.css` 中已有 CSS 变量。
- 新增颜色必须先判断是否能用现有变量表达。
- 不为单个页面发明一套独立配色。
- 不使用大面积紫色渐变、装饰光斑、重阴影背景。
- 深色模式必须保持文字、边框、表单、弹窗和表格可读。

## 留白与间距

使用 `8px` 作为基础间距单位。

推荐间距：

| 场景 | 间距 |
| --- | --- |
| 同组字段之间 | 12px-16px |
| 表单分组之间 | 20px-24px |
| 卡片内部 padding | 16px-24px |
| 页面区块之间 | 24px-32px |
| 后台工具栏与表格之间 | 12px-16px |
| 弹窗内容与底部按钮之间 | 16px-20px |

规则：

- 对齐比装饰更重要。
- 不同区块之间用留白和轻边框区分，不用厚重卡片堆叠。
- 管理后台可以更紧凑，但不能挤到难以扫描。
- 页面左右边距必须一致。

## 对齐规则

- 页面主内容采用统一容器宽度。
- 标题、工具栏、表格左边缘应对齐。
- 表单 label 与输入框左边缘应对齐。
- 表格数字、时间、状态列保持稳定宽度。
- 操作按钮列右对齐或固定宽度。
- 弹窗底部按钮右对齐，取消在左，确认在右。
- 同一组按钮高度、圆角、字号必须一致。

禁止：

- 按钮在同一行上下跳动。
- 表单字段宽度随机。
- 卡片间距一会儿大一会儿小。
- 表格列因为长文本把操作按钮挤出屏幕。

## 按钮规则

按钮分为五类：

- 主按钮：页面最重要的正向操作，例如保存、新增、登录。
- 次按钮：普通操作，例如取消、返回、刷新。
- 幽灵按钮：低强调操作，例如查看详情。
- 危险按钮：删除、关机、重置、清空。
- 图标按钮：主题切换、关闭、更多、刷新。

尺寸规则：

| 类型 | 高度 | 横向 padding | 字号 |
| --- | --- | --- | --- |
| 小按钮 | 32px | 10px-12px | 13px |
| 默认按钮 | 40px | 14px-16px | 14px |
| 大按钮 | 44px-48px | 18px-20px | 15px |
| 图标按钮 | 40px x 40px | 0 | 16px 图标 |

交互规则：

- 按钮必须有 hover、focus、active、disabled 状态。
- 请求提交期间按钮必须进入 loading 或 disabled 状态。
- 同一页面主按钮数量要克制，一个区域通常只保留一个主按钮。
- 危险按钮不能和普通按钮视觉相同。

## 表单布局

默认使用垂直表单：

```text
Label
[ Input ]
Help or error text
```

规则：

- label 放在输入框上方，后台复杂筛选区可以使用水平紧凑布局。
- 输入框默认高度 `40px`。
- textarea 最小高度 `96px`。
- select、input、button 高度必须对齐。
- 必填项用清晰但克制的标记，不用大面积红色。
- 错误信息放在字段下方，说明如何修正。
- 表单提交按钮放在表单底部或弹窗底部固定操作区。
- 表单校验先做必要前端校验，最终以后端校验为准。

后台表单：

- 弹窗内表单最大宽度建议 `640px`。
- 两列表单只用于字段较多且桌面空间充足时。
- 两列表单中跨行字段必须占满整行。
- 搜索筛选表单应短、平、快，不做复杂嵌套。

## 表格与列表

管理后台以表格为主。

表格规则：

- 表格上方必须有工具栏：标题、筛选、刷新、新增等。
- 表头固定使用较强字重。
- 行高保持稳定，默认 `44px-52px`。
- 状态使用 badge，不只靠颜色表达。
- 操作列放在最后，宽度固定。
- 列过多时表格容器横向滚动，不撑破页面。
- 空数据必须显示空状态文案和可选操作。
- 加载中必须显示 skeleton、loading 文案或遮罩。
- 请求失败必须显示错误状态和重试入口。

列表或卡片规则：

- 卡片只用于导航入口、设备状态、概览信息。
- 不做卡片套卡片。
- 卡片标题、状态、说明和操作位置必须统一。

## 弹窗与抽屉

弹窗用于新增、编辑、确认、查看详情。

尺寸建议：

- 小弹窗：`420px-480px`
- 默认弹窗：`560px-640px`
- 大弹窗：`760px-840px`

规则：

- 弹窗最大高度不超过 `calc(100vh - 96px)`。
- 内容超出时弹窗内容区滚动，头部和底部按钮区保持可见。
- 右上角必须有关闭按钮。
- `Esc` 可关闭非强制弹窗。
- 危险确认弹窗必须明确说明影响。
- 弹窗打开时背景不可滚动。

## 状态与反馈

所有请求型页面必须处理：

- 初始加载
- 加载成功
- 空数据
- 请求失败
- 提交中
- 提交成功
- 提交失败
- 按钮禁用

反馈规则：

- 成功反馈可以使用 toast，但重要结果也要在页面上反映。
- 错误反馈不能只使用 `alert` 或控制台。
- 网络错误、权限错误、参数错误应尽量给不同文案。
- 删除、关机、重启、覆盖保存必须二次确认。

## 导航与路径感

- 用户必须知道当前所在模块。
- 后台页面必须有清晰 tab、侧边栏或面包屑。
- 普通页面可使用返回入口或页面标题建立路径感。
- 不在多个位置重复放同级导航，避免用户迷失。

## 可访问性与可用性

- 所有可点击元素必须可通过键盘 focus。
- focus 状态必须可见。
- 图标按钮必须有 `aria-label` 或 `title`。
- 表单字段必须有 label。
- 颜色不能作为唯一状态表达。
- 点击目标不小于 `40px`。
- 文本不能因为容器缩小而重叠。

## 组件复用与提取标准

满足以下任一条件时，应提取公共能力：

- 同一头部或底部结构出现在两个以上页面。
- 同一种按钮、表单、表格、弹窗样式出现在两个以上页面。
- 同一类请求、toast、confirm、loading、empty、error 逻辑重复出现。
- 同一段 HTML 结构复制超过两次。

提取方式：

- 公共 CSS 放入 `src/main/resources/static/css`。
- 公共 JS 放入 `src/main/resources/static/js`。
- Thymeleaf fragment 放入 `src/main/resources/templates/fragments`。
- 页面私有逻辑保留在页面专属 JS 或页面内脚本中。
- 不新增随意的全局命名空间；项目级能力优先挂到 `window.HomeCenter`，后台能力可挂到明确命名的后台命名空间。

## AI 开发检查清单

AI 新增或重构页面前必须检查：

- 是否阅读了 `docs/UI_DESIGN.md`。
- 是否复用了 `/css/app-theme.css` 的变量和基础组件。
- 是否需要 Thymeleaf fragment 复用头部和底部。
- 是否避免引入新框架、外部 CDN 和构建步骤。
- 是否明确页面是桌面端、移动端还是两者都要支持。
- 是否处理了加载、空数据、错误、提交中和成功状态。
- 是否对动态 HTML 内容做了转义。
- 是否避免伪功能。
- 是否统一了按钮尺寸、表单高度、字号和间距。
- 是否检查了头部和底部不会遮挡内容。
- 是否检查了控制台错误。
- 是否检查了中文没有乱码。
- 是否确认文件以 UTF-8 保存，HTML 是否声明 UTF-8。

## UI 设计验收清单

从产品和 UI 角度验收页面时，逐项检查：

- 页面第一眼能否看出当前模块和主要任务。
- 主操作是否足够明确，次要操作是否被弱化。
- 危险操作是否被隔离并二次确认。
- 标题、工具栏、表格、表单是否左边缘对齐。
- 同类按钮是否大小一致。
- 同类输入框是否高度一致。
- 表格是否可扫描，操作列是否稳定。
- 弹窗是否可关闭、可滚动、不溢出。
- 留白是否均匀，是否存在局部拥挤。
- 颜色是否克制，是否有不必要的强对比色。
- 字号层级是否稳定。
- 深色模式是否可读。
- 登录页和导航页在手机端是否可用。
- 管理后台在桌面端是否无明显横向错乱。

## 重构验收标准

每次重构完成后至少验证：

- 页面无明显重叠、遮挡、溢出、错位。
